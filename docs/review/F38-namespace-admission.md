# F38 finite locker, lock and subscription namespaces

Red reproduction through the configured ServerCore graph: ten concurrent creations were all accepted with maxLockers=3. The resource budget existed in configuration but was not applied to the store.

Locker, lock and subscription stores now receive graph limits and serialize growth checks under shared database owners. Room mutation owners precede global admission owners; an existing reservation can be updated at capacity. Locker tombstones and retired lock epochs count as permanent namespace reservations. Stock delete store methods retain history, preserving locker versions/lock epochs instead of erasing rows. A rejected mixed existing/new batch rolls back every change. Subscription counts are finite globally, per session and per room (at most1024 room recipients). Indexed subscription reads reject historical oversized sets explicitly rather than returning partial recipients. Operator environment limits are parsed strictly.

Validation: isolated baseline concurrent graph test reproduces10accepted versus3expected. NamespaceAdmissionTest covers concurrent admission, existing updates, content retirement, permanent capacity after retirement, mixed-batch rollback, retired epoch retention and global/per-room/per-session subscriptions. NamespaceAdmissionPgTest runs against actual PostgreSQL with two independently opened handles and simultaneous reservations across distinct rooms; exactly3locker and3lock reservations succeed, with RESOURCE_EXHAUSTED for the rest. Snapshot and inbox paging regressions pass together. The PostgreSQL test requires LOCKERS_POSTGRES_TEST_URL; the captured run configured the private fixture and had no skipped tests.
