# F06: stop automatic replacement before revocation

Independent review identified a delayed-reply race. The actual HTTP regression `ReviewDestroyReconnectTests.revocationClosesReconnectBeforeADelayedServerReply` registers subscriptions/push, lets the server revoke the current session and close its watch, but holds the successful destroy response for2.5 seconds. Before the fix the client stayed active and reconnected; the terminal-state assertion failed. A second regression cancels a held revocation attempt and verifies that explicit retry targets the same identity; the baseline failed its closed-state assertion.

`Stream.destroySession` serializes attempts, captures the immutable session ID and cancels/joins stream reconnect/reconciliation before sending the signed unary request. It signs against the retained stored identity after shutdown, uses a fresh nonce for explicit retry, and clears sequence/identity only on confirmed success. Uncertain or cancelled attempts retain identity while staying terminal locally. `LockersClient.destroySession` joins all owned children in cancellation-safe cleanup even when the RPC fails. The caller-owned RPC transport remains available for explicit retry.

Both actual HTTP regressions and existing session-proof coverage pass (3 tests). No signing preimage, server authority, or wire field changes. Root combined/platform verification remains a final gate. Restarting an application with a newly constructed client is an explicit new client lifetime; this change prevents automatic replacement by the client being destroyed.
