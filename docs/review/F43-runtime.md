# F43: authenticated subscription intent ordering

A real CIO HTTP reproduction on `845fbfd` plus actor retirement fix `73656c8` held an old subscribe handler before its authenticated mutation. The SDK canceled that call, sent an unsubscribe for the same session, received success, and erased the durable local intent. Releasing the ordinary cancellable server handler then authenticated and committed the old subscribe, restoring the revoked subscription. The test ran once with zero skips and failed in 0.584 seconds. Cancellation did not order remote effects. The proof commit is `feee986`; `/tmp/runtime-subscription-http-order.log` records its failing result.

Additive signed intent revisions now order ordinary subscriptions and subscription snapshots. A durable per-session/room V2 ledger retains the highest positive revision and desired membership, including unsubscribe tombstones. A lower revision returns `STALE_INTENT` and its current revision without mutation; a matching revision with conflicting desired membership fails with `FAILED_PRECONDITION`. Exact desired-state replay remains idempotent. Session proof consumption, revision persistence, membership, and initial snapshot capture share the database transaction. Continuation pages require the exact current subscribed revision and bind that revision into the token; pages cannot restore membership.

`subscription_revisions` advertises explicit store support. Custom subscription stores receive a public transaction seam and default to unsupported modern revisions instead of silently weakening the guarantee. Revision zero preserves legacy operation only until positive history exists for that session/room. New SDK clients negotiate the capability, persist intent generations before RPC, and guard stale-floor repair against obsolete local generations. Older servers cannot provide this guarantee merely by ignoring the additive fields.

The ledger has finite global and per-session lifetime budgets (`LOCKERS_MAX_SUBSCRIPTION_INTENTS`, default 1,000,000; `LOCKERS_MAX_SESSION_SUBSCRIPTION_INTENTS`, default 10,000). Unsubscribe rows are not evicted to admit new identities. Exhaustion is a permanent namespace condition requiring session replacement or trusted maintenance, rather than an endless retry. Permanent session destruction deletes the ledger with bounded indexed queries; revoked IDs cannot be reused. Server schema V5 adds the sidecar through a V4→V5 migration while preserving frozen V4 definitions and historical revision-zero snapshot token bindings.

Initial validation: eight selected server tests passed with zero failures/skips, including the signed HTTP stale-effect rejection, source+revision rollback, stale/conflicting/exact replay, bounded tombstone admission, SQLite V4 migration/reopen, snapshot paging, session proof checks, and an actual mandatory PostgreSQL test using two handles for concurrent ordering and namespace admission. Logs: `/tmp/runtime-subscription-targeted.log` and `/tmp/runtime-subscription-server-compile.log`. Further snapshot/destruction and combined SDK gates follow this prerequisite commit.

The follow-up deliberately distinguishes desired authority from confirmed membership: an `INVALID_DATA` snapshot response commits the newer desired revision fence, preventing delayed older effects, but creates no active subscription or page lease. Exact same-revision retry after owner repair can succeed. Positive continuation pages check an actual active membership row as well as the desired revision and token binding. Malformed/oversized/public-authority room IDs fail before membership or intent admission, and store identity arrays are frozen before transaction suspension.

Three new regressions failed on `91e696b` in an isolated baseline worktree: signed malformed-room rejection, desired-only fences falsely treated as active pages, and caller mutation of queued identity bytes. The corrected run passed 17 tests with zero failures/skips, including mandatory real PostgreSQL tests and permanent revocation, plus `:server:run:compileKotlin`. Logs: `/tmp/runtime-subscription-input-baseline-red.log`, `/tmp/runtime-subscription-boundaries-final.log`.


The final lock-order audit reproduced a second F43 failure on `91376a7`: a room writer owns the dispatcher mutex before beginning its room transaction, while a signed subscription owns its proof/intent/room transaction before requesting that same mutex. Explicit gates hold these two owners before releasing the writer; both the in-memory monolith and two actual PostgreSQL handles then time out (2 tests, 2 failures, zero skips; `/tmp/runtime-subscription-lock-order-red.log`). Moving only `withIntent` inside the existing dispatcher lock would still invert the signed proof transaction against the monolith backend's transaction owner.

Ordinary subscription now uses the dispatcher's tracked execution context without its key mutex. The session-authority, room and admission transaction continues to atomically guard the desired revision and membership mutation, matching the snapshot path. Dispatcher queue telemetry is measured on entering that context, before intent admission; shutdown continues to account for and drain these operations. The deterministic signed memory/PG tests verify both requests complete, retain the subscription, and reject older revisions. A dispatcher lifecycle test verifies bypassing the key mutex still participates in close/drain and rejects work after shutdown begins.

Validation: `SubscriptionLockOrderTest`, `SubscriptionIntent*`, `SubscriptionHttpOrderingTest`, and `ShardedDispatcherTest`: **17 tests, zero failures/errors/skips**, including required PostgreSQL. `:server:run:compileKotlin` and `git diff --check` pass. Final log: `/tmp/runtime-subscription-lock-order-green.log`.

Legacy custom-store boundary: a custom `SubscriptionStore` that keeps the default `withIntent` implementation supports only trusted revision-zero calls; its callback is not made atomic by the service. The old room dispatcher incidentally serialized ordinary subscription callbacks with writes on that service instance. It did not serialize snapshot callbacks, other service instances/nodes, direct store callers or operations in other rooms, and no public interface or repository documentation promised such a storage guarantee. Removing that incidental same-instance mutex is necessary to avoid the signed-proof transaction inversion. Custom store operations must therefore tolerate concurrent calls and provide their own storage synchronization; implementations advertising revision support must supply the full atomic desired-intent/effect contract. The default production store supplies that transaction. Legacy custom stores remain explicitly capability-false and reject positive revisions.
